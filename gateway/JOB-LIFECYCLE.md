# Job completion, waiting and cleanup (2.6.2)

## Claude, Grok and Codex completion and cancellation

`turn.completed` is detected while reading the CLI stream, rather than after process exit. A short grace period allows normal CLI teardown; the gateway then stops the owned process if it remains running. Text, usage, model/effort observations and command evidence survive an abnormal teardown. A matching session ID, cwd and execution time are required before `task_complete` in the official session JSONL can supplement missing terminal output. An ordinary final-looking agent message alone never proves completion.

Claude uses its official top-level JSON `type: "result"` envelope, including when emitted without a final newline. It keeps JSON mode, the generated session ID and official project-attributed JSONL. Error envelopes remain failures even when the process is stopped deliberately after receiving them. Direct result metadata and partial session text survive cancellation/deadline errors.

Grok uses the ACP `session/prompt` response and requires `stopReason: "end_turn"` for success. Its cancellation acknowledgement grace is five seconds; an unresponsive request then yields to forced cleanup. ACP child and terminal cleanup are bounded, and billing/session-usage observations have independent eight-second limits. Unavailable usage never replaces the original task result. All three providers report observed completion and process cleanup separately.

Cancellation and runtime deadlines use bounded process cleanup rather than waiting indefinitely for `close`. Results expose `completion`, `processCleanup`, and `childCleanedUp`. CLI/terminal stop paths allow up to approximately 14 seconds for root and descendant cleanup, plus Grok's cancellation grace and telemetry windows where applicable; slow disks or OS process inventory can still delay reporting. A confirmed turn is not proof that the user's implementation criteria passed. Inspect errors, command exits and the worktree.

`processCleanupState` distinguishes `verified`, `remaining` and `unverified`. An observed remaining PID still blocks safe implementation completion. Incomplete observation with no observed remaining PID preserves a successful provider result and adds `processCleanupWarning`; it does not prove that every process exited. Further implementation providers in the same request are skipped pending parent review. A single-provider successful turn remains successful, while `handoff` still asks the parent to review workspace/process state. `unverifiedPids` contains PIDs whose exit could not be established; do not mistake them for confirmed running processes.

`stalled_suspected` uses `lastActivityAt` even when a different gateway owns the job. `stallEvidence` reports idle time, threshold and observed terminal signal. CPU idleness is `unavailable` unless actually measured. No stall warning automatically cancels or reruns a job.

## Waiting and transport lifetime

Use `agent_job_wait(job_id, timeout_seconds=25)`. Legacy values through 60 remain accepted, but the actual wait is capped at 25 seconds; `wait.effective_timeout_seconds` reports the cap. Set the host request deadline above this, allowing time for status serialization. Reissue on `wait.timed_out`; aborting the wait does not abort the job.

If the host closes stdin or breaks stdout, accepted work drains under its original runtime deadline and writes its result to disk. A new gateway sharing the installation can query it. Explicit `agent_job_cancel` and OS termination signals still cancel. A host that forcibly terminates the gateway process cannot be prevented from interrupting work. No automatic replay, scheduling or resumed implementation is performed.

Completion push notifications are not enabled: client subscription support and delivery across reconnects are not consistently available. Persisted status plus short bounded waits remain the source of truth; a notification would not replace them.

## Reviewed failed/cancelled worktrees

Preview with `agent_worktree_cleanup(job_id, dry_run=true)`. A failed/cancelled job with commits can be removed only after its tip is an ancestor of the original repository's current HEAD, and the parent supplies `verified=true`, `idle_confirmed=true`, and `verification_summary`. Patch equivalence cannot substitute for ancestry for these failed/cancelled jobs. A fresh Windows/Linux process inventory rejects observable workspace writers and unknown provider ownership; the gateway may remain alive serving unrelated work. Active jobs, dirty targets and unmerged commits remain blocked. Incomplete prior cleanup requires idle_confirmed=true and verification_summary, a fresh check that every tracked/remaining/unverified PID is absent or proven reused, and a fresh workspace ownership scan. Live or uninspectable PIDs still block physical cleanup. Record-only forget uses the separate policy below. Automatic empty-worktree deletion is not allowed while cleanup is unverified. Job outcome, logs and usage are not rewritten as successful.

Add `remove_ignored_artifacts=true` only when the parent intends to discard ignored generated files. Eligibility and integration checks precede deletion. Dry-run returns `ignoredArtifactPaths`; apply returns and persists `removedIgnoredPaths`, including partial deletion if a locked file prevents completion. Only Git-ignored, untracked regular files and empty ignored parent directories are removed. Tracked modifications, ordinary untracked files, links/junctions and nested repositories are refused. No recursive or forced worktree deletion is used. Keep manual writers inactive during cleanup; filesystem changes by unrelated applications cannot be atomically locked by this gateway.

Linux ownership inspection covers the current UID through `/proc`; inaccessible live process details cause refusal, even for a same-user session daemon. Some distributions restrict these details. This can prevent reviewed failed/interrupted or previously unverified cleanup until ownership can be established. The gateway does not whitelist process names or elevate privileges to bypass the restriction. Ordinary verified successful cleanup retains its existing behavior.

## Build processes

Claude, Grok and Codex implementation now reuse the effective user `GRADLE_USER_HOME`, or the user's `.gradle` directory if none is configured. Grok propagates the same home to ACP terminals. No new per-job cache or distribution copy is created. `gradle.cleanup` reports `not_needed`, `removedBytes: 0`; the shared user cache is never deleted. Previously created per-job Gradle homes remain preserved until the parent verifies ownership and performs a separate cleanup. This avoids silently deleting a live daemon's cache or data referenced by an older job.

The implementation prompt asks for `--no-daemon`, preserves build artifacts for the parent's `remove_ignored_artifacts` cleanup, and requires authorization for external downloads. Shared caches use Gradle's normal locking and may contend during parallel builds; this is not per-job cache isolation. Gradle can still start a short-lived single-use process. Captured descendant PIDs are checked against creation identity before termination; unrelated Java/Node processes are never killed merely for sharing a cwd.

`gradle.downloads` reports download lines found in available command output, with credential/query-stripped targets. `not_observed` is not proof of no network traffic, and `networkEnforced` is false: Gateway does not install a network firewall. Missing cached dependencies or a missing Wrapper distribution require parent review before downloading. Gradle's [dependency-cache documentation](https://docs.gradle.org/current/userguide/dependency_caching.html) and [Wrapper documentation](https://docs.gradle.org/current/userguide/gradle_wrapper.html) describe these separate caches. No task-local directory is created merely to make `--offline` appear isolated.

Install using the signed 2.6.3 release and the existing Monitor updater or ZIP `Update.ps1`. Linux/WSL uses its separate signed package and `agent-acp update` after first-time installer registration. Finish active work before replacement, preserve state, and reconnect MCP. No provider CLI, authentication scheme, self-provider default, or model policy is changed.


## Process identity and historical PID reuse

All three providers retain `processCleanup.trackedProcesses` and root identities: PID, UTC `createdAt`, `imageName`, `observedAt` and an OS creation key. Windows uses one CIM inventory per verification pass (including ancestors); Linux uses `/proc` start ticks and boot identity. A PID number alone is not process identity. Equal creation identity is `alive`; different creation is `reused`. Inaccessible creation data is `unknown` and blocks maintenance.

Older jobs without identities use `startedAt` through `finishedAt` (or cleanup observation time). A current birth outside that interval proves reuse. A birth inside the interval requires a complete, creation-consistent current parent chain with no tracked or root anchor. The recorded Gateway owner is an additional ancestry anchor, labeled separately from observed provider roots. Missing/dead parents, cycles or unreadable birth data remain unknown; a familiar image name is never an exemption. Legacy ancestry is less definitive than recorded creation identity, so workspace ownership scanning and parent idle confirmation remain required.

Dry runs return `trackedProcessCheck.checks`; refused requests return `processCheck.checks`, including current image/time, recorded time, decision and reason for each PID. Bulk cleanup retains these diagnostics. `forget` requires fresh proof that the path, branch and registration are all absent. PID warnings then require explicit `acknowledge_process_warning=true` for apply, alongside `verified=true` and `verification_summary`. They are retained under `worktree.forgetAudit`, including per-PID checks and acknowledgement time; process cleanup is never relabeled verified. Job status/results, original PID evidence and payload artifact references are unchanged. `idle_confirmed` remains accepted for compatibility but does not replace warning acknowledgement. Active/finalizing records, concurrent maintenance, changing records, unreadable full evidence and unknown filesystem/ref absence remain blocked. Orphaned records require confirmed absent Gateway ownership and retain their original persisted status. No processes are terminated. `include_removed=true`, worktree status and job status retain the audit after the normal worktree list hides the record.

Compacted `processCleanup` includes `trackedPidCount`, `truncated` and `trackedPidsPath`. Both job and worktree status return `processEvidence.file`, pointing to the complete snapshot. Legacy previews are hydrated read-only to recover the true count; failed hydration reports unavailable evidence rather than treating the preview as complete.

## Explicit cleanup of old task Gradle homes

Use `agent_legacy_gradle_list` to see obsolete UUID directories, size, associated jobs and blockers. `agent_legacy_gradle_cleanup(path="<exact listed path>")` defaults to `dry_run=true`. After reviewing the result, pass `dry_run=false` to remove eligible files. This is never automatic. The exact home must be recorded by a finished job's authoritative result; UUID naming alone is insufficient. Active/pending jobs, missing job evidence, live/unknown ownership, unsafe paths, symlinks/junctions and hardlinks block deletion. The default user Gradle home and configured shared-cache aliases are protected.

Successful cleanup reports removed paths and bytes, and leaves job records/results/branches untouched. A filesystem failure reports partial removal and retained paths. The Gateway serializes this operation against new local job starts and rechecks shared job/process state before deletion; keep unrelated manual writers idle as they cannot be atomically locked. Legacy homes not attributable to a retained job stay preserved.
