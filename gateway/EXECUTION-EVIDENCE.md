# Execution outcome and progress metadata

`outcome: success` means selected provider turns completed without a reported execution error. It does not certify the user's acceptance criteria. This meaning is explicit in `outcomeMeaning: provider_turn_execution_only` and `completionCriteria: {status: unverified, requiresParentReview: true}`. Parent reviews changes, requirements and test evidence before declaring the whole task complete.

Each provider result has `execution.turnStatus` and `execution.commands`. The latter counts observed command exit codes (succeeded/failed/unknown) and reports `not_observed`, `incomplete`, `mixed`, `failed`, or `all_exited_zero`. A failed command followed by a successful retry remains `mixed`: the parent decides whether the later command covers the earlier failure. No test counts are inferred from assistant text or exit codes. This is common to Grok, Claude and Codex; absent observations are explicit.

Grok `exitCode` remains a compatibility alias for the ACP child process exit, not Gradle/test/task status. `exitCodeMeaning` identifies it. `processExit` captures code, signal, phase, timestamp, whether gateway shutdown was intentional, and whether the prompt response had arrived. `processWarnings` surfaces a nonzero process exit even after a completed turn; it is not silently converted to zero. Intentional shutdown describes gateway action, not proof of why the CLI exited. A process failure before completion remains a task failure. Existing saved jobs are not rewritten and cannot supply missing historical exit timing.

`agent_job_status.implementationProgress` exposes successful ACP file reads/writes and terminal starts. After at least 300 seconds and 20 successful reads, with no successful write or terminal start, it reports `exploration_without_observed_execution`, a warning, and `nextAction: parent_review_scope_and_next_step`. This is distinct from no-activity stall detection. Counters cover observed ACP client operations, not every possible file modification. Rejected writes do not count as progress. The timer is frozen at job completion, and persisted metadata can be read by another MCP process. It never cancels, retries, schedules, changes effort or modifies the task automatically.

Parent response to the warning: inspect current changes and the concrete blocker; request a bounded compile fix or next verification step when appropriate. Do not automatically replay an implementation or force speculative edits. Claude/Codex and old jobs without structured progress return `unavailable` rather than invented counts. These changes improve visibility; provider inference speed improvement has not been measured.

MCP reconnect is required to load the new code. Do not terminate ongoing jobs for an update.
